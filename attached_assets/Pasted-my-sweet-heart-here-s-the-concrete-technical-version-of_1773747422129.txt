## What the system actually is

This should be a **web application with a browser frontend and a backend analysis engine**.

The frontend does:

* file upload
* preview
* progress/status
* shows coverage results
* takes yield and price inputs
* calculates cost estimate
* shows variation range

The backend does:

* reads the uploaded file
* converts it into analyzable pages/images
* calculates ink coverage
* returns structured results
* stores optional estimate history/report data

So the core idea is:

**Frontend UI → upload file → backend analysis → coverage response → cost calculation UI**

## Mobile future

Do **not** build the analysis logic into the frontend.

Instead:

* keep all analysis in the backend API
* make the frontend a client of that API

Then later:

* React Native app can call the same API
* no need to rewrite analysis engine
* only UI changes, not core print logic

So the architecture should be **API-first** from day one.

## 2. Backend creates an analysis job

The API creates a job record like:

```json
{
  "job_id": "abc123",
  "status": "queued",
  "mode": "cmyk",
  "file_type": "pdf"
}
```

For larger files, the backend should process asynchronously.

Statuses:

* queued
* processing
* completed
* failed

Frontend polls or subscribes for updates.

---

## 3. File is converted into pages/images

This is the important part.

### If the upload is a PDF

The backend must render each page into a raster image at a fixed DPI.

Recommended:

* 150 DPI for fast preview
* 300 DPI for analysis
* possibly selectable

Why render?
Because coverage estimation becomes much easier once each page is a bitmap.

### If the upload is an image

Normalize it:

* flatten transparency onto white background if needed
* standardize resolution
* standardize color space
* standardize bit depth if needed

---

## 4. Normalize color space

This is where accuracy depends heavily on discipline.

Every page/image should be normalized into a known working space.

### For RGB-origin files

Convert to:

* sRGB working space first for consistency

### For CMYK-like estimate mode

Then convert into a CMYK profile using an ICC transform.

This is critical:

* different devices and RIPs produce different CMYK separations
* so there is no universal CMYK truth for all files
* you need a chosen reference profile

Example:

* ISO Coated v2
* US Web Coated SWOP
* device-specific profile supplied by the distributor/vendor

This is why “100% accurate” is not universal.

It can only become highly accurate when tied to:

* a specific printer
* a specific paper
* a specific print mode
* a specific ICC profile
* a specific driver or RIP path

---

## 5. Calculate coverage

Coverage means:

**What percentage of the printable area is occupied by ink/toner for each channel?**

### In CMYK mode

For each page:

* get C, M, Y, K channel values
* sum pixel intensity per channel
* divide by total possible channel value
* convert to percentage

Conceptually:

```text
coverage_channel % =
(sum of channel ink values across all pixels) /
(max possible channel ink value across all pixels)
× 100
```

If image uses 8-bit channels:

* each pixel channel ranges 0–255
* normalize accordingly

### Example

If a page has 1,000,000 pixels, then max cyan total is:

```text
1,000,000 × 255
```

If the actual cyan sum is 63,750,000:

```text
63,750,000 / 255,000,000 = 0.25 = 25%
```

So cyan coverage is 25%.

### In Color + Black cartridge mode

You have two possible models:

#### Model A: black separate, color combined

* black = K channel
* color = average or combined load of C, M, Y

A more realistic approach:

```text
color_load = (C + M + Y) / 3
black_load = K
```

#### Model B: driver simulation

Some consumer printers mix CMY and black differently depending on driver logic.
That means:

* text may use mostly black
* photos may use more color
* dark regions may blend color + black

This requires printer-specific heuristics or measured calibration tables.

For a promo estimator, start with **Model A**.

## 6. Compute per-page and document-level results

For each page, return:

* page number
* cyan %
* magenta %
* yellow %
* black %
* total area coverage
* optional page preview thumbnail

Then compute document-level results:

* average coverage across all pages
* total ink load across all pages
* min/max coverage page
* estimated print complexity category

Example response:

```json
{
  "job_id": "abc123",
  "pages": [
    {
      "page": 1,
      "cyan": 12.4,
      "magenta": 9.1,
      "yellow": 8.7,
      "black": 18.3
    }
  ],
  "summary": {
    "avg_cyan": 11.8,
    "avg_magenta": 8.9,
    "avg_yellow": 8.1,
    "avg_black": 17.6
  }
}
```

## 7. Cost estimation logic

This is separate from coverage analysis.

Manufacturers usually state cartridge yield at **5% page coverage**.

So cost calculation should be based on scaling yield by actual coverage.

### Formula

If:

* cartridge yield = 1000 pages at 5%
* actual page coverage = 20%

Then actual yield is approximately:

```text
effective_yield = rated_yield × (5 / actual_coverage)
```

Example:

```text
effective_yield = 1000 × (5 / 20) = 250 pages
```

If cartridge price is $20:

```text
cost_per_page = 20 / 250 = $0.08
```

### CMYK total

Do this separately for C, M, Y, K and sum them.

```text
total_cost = cyan_cost + magenta_cost + yellow_cost + black_cost
```

### Color + Black cartridge

Do this for:

* color cartridge
* black cartridge

Then sum them.

---

## 8. Variation / waste model

This should never be hidden. It should be explicit.

Real printing has:

* cleaning cycles
* priming
* alignment wastage
* edge loss
* non-printable margins
* test prints
* driver behavior differences
* environmental variation

So add a configurable waste factor.

### Formula

```text
adjusted_cost = base_cost × (1 + waste_percent / 100)
```

Example:

* base cost = $0.10
* waste = 12%

```text
adjusted_cost = 0.10 × 1.12 = $0.112
```

### Range display

Show:

* base estimate
* expected range
* confidence label

Example:

* Base: $0.112/page
* Range: $0.103 to $0.121
* Confidence: Medium

Variation can come from:

* generic default band, like ±8%
* or better, from printer-specific calibration data

---

## 9. How to make it genuinely accurate

The only serious route is calibration.

You need **printer profiles**.

For each supported printer family, store:

* printer model
* cartridge type
* rated yields
* print mode
* paper type
* ICC profile
* waste baseline
* correction multipliers

Then actual estimate becomes:

```text
final_estimate = raw_calculated_cost × printer_calibration_factor
```

Example:

* HP model X on plain paper normal mode = 1.07 multiplier
* Epson model Y on glossy high mode = 1.18 multiplier

This is how the app becomes commercially credible.

Without calibration:

* it is an estimate engine
* not a forensic truth engine

* file
* mode
* optional printer_profile_id

```json

  "job_id": "abc123",
  "status": "queued"
```

```http
GET /api/jobs/{job_id}
```

Response:

```json
{
  "job_id": "abc123",
  "status": "processing",
  "progress": 60
}
```

## Results endpoint

```http
GET /api/jobs/{job_id}/results
```

Response:

```json
{
  "summary": {
    "avg_cyan": 12.1,
    "avg_magenta": 7.8,
    "avg_yellow": 6.4,
    "avg_black": 19.5
  },
  "pages": [...]
}
```

```http
POST /api/estimates/cost
```

* signed upload URLs

* rate limiting
* file expiry cleanup
* audit logging
* encryption at rest
* HTTPS only

## 16. What “100% accurate” would require

If someone insists on that phrase, the only honest wording is:

**“Profile-based coverage estimation with printer-specific calibration.”**

Because true absolute accuracy would require knowing:

* printer model
* driver
* RIP behavior
* media
* resolution
* ICC path
* maintenance state
* environmental conditions
* actual ink deposition behavior

That is beyond a generic website unless you build a calibrated ecosystem.
